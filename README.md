# Energytool — AI-консультант МТС

Прототип ведёт клиента от описания задачи до заявки специалисту. Он ищет сведения в предоставленной базе знаний, отвечает с учётом истории диалога, задаёт уточняющие вопросы, не выдумывает отсутствующие факты и сохраняет все сессии локально.

> Данные из `knowledge-base/` предназначены только для выполнения задания. Не публикуйте базу знаний и её копии в открытых репозиториях.

## Быстрый запуск через Docker

Требования: Docker Desktop, запущенная Ollama и модель `qwen3:8b`.

```powershell
ollama pull qwen3:8b
docker compose up --build
```

После запуска откройте <http://localhost:8000>. Проверка состояния: <http://localhost:8000/api/health>. Swagger API: <http://localhost:8000/api/docs>.

Приложение в контейнере обращается к Ollama на компьютере через `host.docker.internal:11434`. История сохраняется в локальной папке `sessions/` и не пропадает при пересоздании контейнера.

Остановка:

```powershell
docker compose down
```

## Основной сценарий проверки

1. Откройте <http://localhost:8000>.
2. Включите «Режим отладки» — после ответа появятся время обработки и документы, использованные RAG.
3. Спросите: «Как контролировать энергопотребление на нескольких объектах?»
4. Продолжите диалог уточняющей репликой и убедитесь, что контекст сохранён.
5. Напишите: «Хочу связаться с менеджером».
6. По очереди укажите вымышленные ФИО, телефон и компанию.
7. Убедитесь, что показана сформированная заявка с резюме.
8. Откройте историю диалогов, затем нажмите «Новый диалог»: новый чат должен быть пустым, старый — оставаться в архиве.

Используйте только тестовые или вымышленные персональные данные.

## Возможности

- BM25-поиск по базе знаний и опциональный векторный/гибридный режим;
- ответы только на основе найденных материалов;
- уточняющий вопрос при недостатке данных;
- корректный отказ для тем вне компетенции;
- контекст многошагового диалога;
- сбор ФИО, телефона и компании с проверкой номера;
- человекочитаемое резюме заявки;
- сохранение всех разговоров в JSON, включая разговоры без заявки;
- новый диалог без удаления предыдущей истории;
- веб-чат, адаптированный для компьютеров и телефонов;
- режим отладки с временем ответа и источниками;
- REST API для встраивания в сайт;
- отдельная точка входа для автоматической проверки хакатона.

## Архитектура

```text
Браузер
   │ HTTP/JSON
   ▼
FastAPI (web/app.py)
   │
   ▼
EnergytoolAI (integration/interface.py)
   ├── ConversationState ──► sessions/*.json
   └── EnergytoolConsultant
       ├── lead workflow
       ├── Retriever ───────► knowledge-base/
       └── LLMClient ───────► Ollama или OpenAI-compatible API
```

Ключевые компоненты:

- `web/app.py` — HTTP API и раздача интерфейса;
- `web/static/` — HTML/CSS/JavaScript без отдельной сборки Node.js;
- `consultant/consultant.py` — сценарий консультации, ограничения и сбор заявки;
- `rag/retrieval.py` — поиск и подготовка контекста;
- `llm/qwen.py` — Ollama/OpenAI-совместимый клиент;
- `memory/conversation_state.py` — атомарное JSON-хранилище сессий;
- `integration/interface.py` — стабильный интерфейс AI-ядра;
- `solution.py` — независимая точка входа ZIP-сабмита.

## REST API и встраивание

Основной вызов:

```http
POST /api/chat
Content-Type: application/json

{
  "message": "Нужно контролировать потребление на объектах",
  "session_id": null,
  "debug": true
}
```

Ответ содержит `answer`, `status`, `sources`, `session_id`, `lead` и `debug`. Следующую реплику нужно отправлять с полученным `session_id`.

Дополнительные методы:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | состояние приложения |
| `POST` | `/api/sessions` | новый чистый диалог |
| `GET` | `/api/sessions` | список сохранённых сессий |
| `GET` | `/api/sessions/{id}` | история и заявка выбранной сессии |

Для сайта Energytool интерфейс можно встроить как отдельный виджет, отправляющий запросы этому API. В промышленной версии вместо локального JSON-хранилища подключается БД, а завершённые заявки передаются в CRM через адаптер или очередь. Текущий прототип намеренно не отправляет персональные данные наружу.

## Переменные окружения

Шаблон находится в `.env.example`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_PORT` | `8000` | внешний порт Docker |
| `LLM_PROVIDER` | `ollama` | `ollama` или `openai` |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Ollama при запуске без Docker |
| `DOCKER_OLLAMA_BASE_URL` | `http://host.docker.internal:11434` | Ollama из контейнера |
| `OLLAMA_MODEL` | `qwen3:8b` | локальная модель |
| `LLM_BASE_URL` | пусто | URL OpenAI-совместимого API |
| `LLM_API_KEY` | пусто | ключ API; не добавлять в Git |
| `LLM_MODEL` | `qwen/qwen3.8-27b` | модель внешнего API |
| `LLM_TIMEOUT` | `120` | тайм-аут, секунд |
| `RETRIEVER_MODE` | `bm25` | `bm25`, `vector`, `hybrid` или `auto` |
| `SESSION_DIR` | `sessions` | каталог истории |

Рабочие ключи и пароли нельзя сохранять в `.env.example`, исходном коде, логах или ZIP-архиве.

## Зависимости и тесты

Версии зафиксированы в `requirements.txt`. Веб-прототип использует FastAPI, Uvicorn, HTTPX, NumPy и python-dotenv. Для локальных embeddings отдельно предусмотрен `requirements-embeddings.txt`.

Запуск тестов:

```powershell
& ".\.venv\Scripts\python.exe" -m unittest discover -s tests -v
```

Тесты проверяют загрузку базы, BM25, разбор диалога, формат сабмита, защиту `session_id`, API, приветствие и полный сценарий заявки.

## ZIP-сабмит для автоматической оценки

Сборка плоского архива:

```powershell
& ".\.venv\Scripts\python.exe" ".\build_submission.py"
```

Результат: `dist/energytool_submission.zip`. В корне архива находятся `solution.py`, зависимости и необходимые плоские Python-модули. База знаний и ключи в архив не включаются: платформа передаёт их через `DATA_DIR` и переменные окружения.

`solution.py` читает `questions.csv`, находит и распаковывает `knowledge-base.zip`, обрабатывает каждый ID независимо и создаёт `submission.csv` с колонками `id,answer`. Для платформы используются `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `MAX_WORKERS`, `TEMPERATURE`, `MAX_TOKENS`, `TOP_K` и другие предусмотренные регламентом параметры.

## Известные ограничения

- BM25 хуже понимает перефразированные запросы, чем проверенный гибридный поиск.
- Скорость генерации зависит от модели и оборудования; первый локальный ответ может быть медленнее из-за загрузки модели.
- JSON-хранилище подходит для демонстрации, но не для нескольких экземпляров приложения и высокой нагрузки.
- Авторизация, шифрование персональных данных и реальная CRM-интеграция в прототипе отсутствуют.
- Заявка сохраняется локально и не отправляется менеджеру автоматически.
- Качество ответа ограничено полнотой предоставленной базы знаний; при отсутствии фактов бот должен отказать или предложить специалиста.
