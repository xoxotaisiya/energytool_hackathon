# Energytool — AI-консультант в сфере энергетики

## 1. О проекте

**Energytool** — AI-консультант в сфере энергетики, разработанный на основе технологии RAG (Retrieval-Augmented Generation) и языковой модели Qwen.

Задача проекта — помогать пользователям получать ответы на вопросы об энергетике, энергопотреблении, потерях, энергоэффективности и продуктах МТС на основе подготовленной базы знаний.

В отличие от обычного чат-бота, Energytool использует внутреннюю базу знаний для поиска информации, необходимой для ответа. Это позволяет опираться на материалы проекта, а не только на общие знания языковой модели.

Основные возможности AI-ядра:

- поиск информации в базе знаний;
- извлечение релевантных фрагментов документов;
- передача найденной информации в языковую модель;
- формирование ответа с учётом контекста запроса;
- обработка ситуаций, когда информации недостаточно;
- поддержка контекста диалога;
- передача статуса обработки запроса во внешний интерфейс.

Текущая версия представляет собой AI-ядро с консольным запуском и программным интерфейсом для последующей интеграции с Web-приложением.

## 2. Архитектура и принцип работы

В основе Energytool лежит архитектура RAG, объединяющая поиск по базе знаний и генерацию ответа с помощью языковой модели.

Обработка запроса проходит несколько этапов:

1. Пользователь отправляет вопрос.
2. Система принимает запрос и подготавливает его для поиска.
3. RAG-модуль ищет подходящие фрагменты в базе знаний.
4. Наиболее релевантная информация передаётся в контекст языковой модели.
5. Qwen формирует ответ на основе вопроса и найденных материалов.
6. Система возвращает ответ, статус обработки и доступную информацию об источниках.

### Общая схема

```text
Пользователь
     |
     v
Интерфейс приложения
     |
     v
Интеграционный интерфейс
     |
     v
Energytool AI Core
     |
     +----------------------+
     |                      |
     v                      v
 RAG-модуль             Memory
     |                Контекст диалога
     v
 База знаний
     |
     v
 Retrieval
     |
     v
 Релевантные фрагменты
     |
     v
 Qwen через Ollama
     |
     v
 Формирование ответа
     |
     v
 Ответ + статус + источники
```

Основные части системы разделены на независимые модули. Это позволяет изменять механизм поиска, языковую модель или интерфейс интеграции без необходимости переписывать всё приложение.

## 3. RAG: поиск и подготовка информации

RAG (Retrieval-Augmented Generation) — подход, при котором языковая модель формирует ответ с использованием информации, предварительно найденной во внешней базе знаний.

В Energytool RAG отвечает за поиск материалов, которые могут помочь ответить на вопрос пользователя.

### 3.1. Подготовка базы знаний

Исходные материалы хранятся в директории `knowledge-base/`.

Перед использованием документы подготавливаются для поиска: текст разделяется на отдельные фрагменты (chunks), с которыми далее работает поисковый модуль.

Разделение на фрагменты позволяет передавать языковой модели только подходящие части документов, а не всю базу знаний целиком.

Для подготовки фрагментов используется:

`rag/build_chunks.py`

### 3.2. Retrieval — поиск релевантной информации

Retrieval — этап поиска фрагментов базы знаний, наиболее подходящих к вопросу пользователя.

В текущей конфигурации основным способом поиска является BM25 — алгоритм текстового поиска, который оценивает соответствие документа запросу на основе совпадения слов и их значимости.

Основные файлы:

- `rag/retrieval.py` — запуск поиска и получение результатов;
- `rag/retriever.py` — логика поискового механизма.

Результатом работы Retrieval становится набор найденных фрагментов, которые могут быть использованы для формирования ответа.

Текущая конфигурация использует BM25. Это важно учитывать при оценке качества: поиск по ключевым словам может не находить материалы, если пользователь формулирует вопрос другими словами.

### 3.3. Embedding и семантический поиск

Embedding — представление текста в виде числового вектора, отражающего его смысловые характеристики.

Семантический поиск позволяет находить материалы не только по совпадению слов, но и по близости смысла запроса и документа.

В проекте предусмотрен компонент:

`rag/embedder.py`

Он предназначен для работы с векторными представлениями текста.

При этом полноценный гибридный поиск BM25 + embeddings в текущей версии не заявляется как реализованный и проверенный механизм. Его подключение и оценка качества относятся к дальнейшему развитию проекта.

### 3.4. Передача контекста в языковую модель

После поиска система получает релевантные фрагменты базы знаний.

Эти материалы передаются в языковую модель вместе с исходным вопросом пользователя и системными инструкциями.

Таким образом, модель получает контекст, необходимый для ответа, вместо того чтобы опираться только на собственные знания.

Количество передаваемых фрагментов ограничивается параметрами поиска. Это помогает контролировать объём контекста и не перегружать языковую модель лишней информацией.

### 3.5. Формирование ответа

На заключительном этапе Qwen получает:

- вопрос пользователя;
- найденные фрагменты базы знаний;
- системные инструкции;
- доступный контекст диалога.

На основе этих данных модель формирует ответ.

Если найденной информации недостаточно, система может запросить уточнение, сообщить об отсутствии подтверждённых данных или передать запрос на дальнейшую обработку.

Основной принцип — не подменять отсутствующую информацию вымышленными фактами.

## 5. Основные компоненты проекта

### 5.1. Модуль RAG

Директория `rag/` содержит компоненты подготовки документов, поиска информации и оценки качества Retrieval.

| Файл | Назначение |
|---|---|
| `build_chunks.py` | Подготовка и разделение документов на фрагменты |
| `retrieval.py` | Запуск поиска по базе знаний |
| `retriever.py` | Реализация поисковой логики |
| `embedder.py` | Компонент для работы с embeddings |
| `evaluate.py` | Оценка работы системы |
| `evaluate_retrieval.py` | Оценка качества поиска |
| `measure_scores.py` | Расчёт оценочных показателей |
| `eval_*.json` | Тестовые данные для оценки |

Файлы оценки используются для проверки и экспериментов. Они не являются частью обязательного пути обработки каждого пользовательского запроса.

### 5.2. База знаний

Директория `knowledge-base/` содержит материалы, на основе которых работает AI-консультант.

База знаний разделена по тематическим направлениям:

| Директория | Содержание |
|---|---|
| `00-reference/` | Справочная информация и исходные материалы |
| `10-energy/` | Материалы по энергетике, энергопотреблению и потерям |
| `20-products/` | Информация о продуктах и решениях |

Материалы хранятся в формате Markdown. Такой формат позволяет структурировать документы, редактировать их и использовать при подготовке данных для RAG.

### 5.3. Работа с языковой моделью

Директория `llm/` отвечает за взаимодействие с языковой моделью.

Основной файл:

`llm/qwen.py`

В качестве языковой модели используется Qwen через локальный сервер Ollama.

Взаимодействие с моделью вынесено в отдельный модуль, чтобы поисковая логика и бизнес-логика консультанта не зависели от конкретной реализации LLM.

Системные инструкции хранятся отдельно:

`prompts/system_prompts.py`

Это позволяет изменять поведение консультанта и правила формирования ответа без изменения поискового механизма.

Фактический запуск Qwen и полный сквозной сценарий необходимо проверять в рабочем окружении с установленной и запущенной Ollama.

### 5.4. Память диалога

Директория `memory/` отвечает за хранение состояния диалога.

Основной файл:

`memory/conversation_state.py`

Контекст диалога позволяет учитывать предыдущие сообщения при продолжении общения.

Идентификатор сессии используется для связи последовательных запросов одного диалога.

### 5.5. Остальные файлы

## 6. Интеграционный интерфейс

### Подключение AI-ядра к бэкенду

Для интеграции с Web-приложением предусмотрен отдельный интерфейс:

`integration/interface.py`

В нём реализован класс `EnergytoolAI`, через который внешний бэкенд может отправлять сообщения в AI-ядро и получать результат обработки.

**Разработчику бэкенда рекомендуется использовать именно этот интерфейс.**

Не требуется напрямую подключать внутренние модули RAG, LLM, Memory или Prompt. Они уже входят в состав AI-ядра и вызываются внутри него.

Основной метод:

```python
EnergytoolAI.chat(message, session_id=None)
```

Параметры:

| Параметр | Описание |
|---|---|
| `message` | Текст сообщения пользователя |
| `session_id` | Идентификатор текущего диалога; используется для продолжения сессии |

Пример использования:

```python
from integration.interface import EnergytoolAI

ai = EnergytoolAI()

result = ai.chat(
    message="Как можно снизить потери электроэнергии?",
    session_id="user-session-001"
)

print(result["answer"])
print(result["status"])
```

### Формат ответа интеграционного интерфейса

Интерфейс возвращает структурированный результат:

```json
{
  "answer": "Текст ответа AI-консультанта",
  "status": "answered",
  "question": null,
  "sources": [],
  "session_id": "user-session-001",
  "debug": null
}
```

Назначение полей:

| Поле | Описание |
|---|---|
| `answer` | Сформированный текст ответа |
| `status` | Результат обработки запроса |
| `question` | Уточняющий вопрос, если он требуется |
| `sources` | Информация об источниках, доступная от системы |
| `session_id` | Идентификатор диалога |
| `debug` | Дополнительная техническая информация |

### Статусы обработки

| Статус | Значение | Действие бэкенда |
|---|---|---|
| `answered` | Ответ сформирован | Показать ответ |
| `clarification_needed` | Не хватает информации для уточнения запроса | Показать уточняющий вопрос |
| `no_evidence` | В базе знаний не найдено достаточных подтверждений | Сообщить об ограничении |
| `out_of_scope` | Запрос вне предметной области консультанта | Объяснить границы компетенции |
| `handoff` | Требуется передача специалисту | Запустить сценарий обращения |
| `error` | Ошибка обработки | Обработать ошибку |

### Что необходимо реализовать на стороне бэкенда

Бэкенд отвечает за внешнюю часть приложения и взаимодействие с пользователем.

Необходимо реализовать:

1. Приём сообщений из Web-интерфейса.
2. Вызов `EnergytoolAI.chat()`.
3. Передачу и сохранение `session_id` между сообщениями.
4. Обработку статусов ответа.
5. Отображение ответа и уточняющих вопросов.
6. Сценарий обращения к специалисту, если он предусмотрен продуктовой логикой.
7. Сбор ФИО, телефона и названия компании при оформлении заявки.
8. Хранение и передачу заявок во внешнюю систему, если это предусмотрено интеграцией.

### Что не нужно подключать напрямую

Бэкенду не требуется напрямую обращаться к следующим внутренним компонентам:

- `rag/retrieval.py`;
- `rag/retriever.py`;
- `rag/build_chunks.py`;
- `rag/embedder.py`;
- `llm/qwen.py`;
- `memory/conversation_state.py`;
- `prompts/system_prompts.py`;
- модулям оценки качества в `rag/`.

Они являются внутренними частями AI-ядра.

`main.py` предназначен для консольного запуска, а не для интеграции с Web-приложением.

`solution.py` не следует использовать как готовый адаптер конкурсной платформы без отдельной проверки его соответствия требованиям организаторов.

**Граница ответственности:** AI-ядро отвечает за поиск информации и формирование ответа. Бэкенд отвечает за Web-интерфейс, пользовательские сессии на уровне приложения, формы, контактные данные, заявки и внешние интеграции.

## 7. Форматы данных

В проекте используются разные форматы в зависимости от назначения данных.

| Формат | Где используется | Для чего |
|---|---|---|
| Markdown (`.md`) | `knowledge-base/` | Хранение и структурирование базы знаний |
| JSON (`.json`) | `eval_*.json`, данные состояния и конфигурации, где применимо | Структурированные данные, тестовые сценарии и вложенные объекты |
| CSV (`.csv`) | Табличные наборы данных и выгрузки, если используются | Хранение данных в виде строк и столбцов |
| Python (`.py`) | Все программные модули | Логика приложения |
| TXT (`.txt`) | Служебные текстовые материалы, если используются | Текстовые данные без сложной структуры |

Markdown используется для базы знаний, поскольку он удобен для редактирования и разделения информации по темам.

JSON подходит для структурированных объектов, тестовых наборов и результатов обработки.

CSV удобен для табличных данных и выгрузок, которые требуется анализировать или обрабатывать отдельно.

Формат submission для конкурсной платформы должен определяться требованиями организаторов. Нельзя заранее считать, что платформа принимает именно JSON или CSV.

## 8. Оценка качества модели и поиска

Качество Energytool зависит от нескольких компонентов:

- полноты и актуальности базы знаний;
- качества подготовки документов и разделения на фрагменты;
- релевантности найденной информации;
- корректности передачи контекста в Qwen;
- соблюдения моделью системных инструкций;
- качества обработки уточнений и недостатка данных.

Для оценки предусмотрены отдельные тестовые и измерительные модули в директории `rag/`.

В частности:

- `evaluate_retrieval.py` — проверка качества поиска;
- `measure_scores.py` — расчёт оценочных показателей;
- `eval_*.json` — тестовые данные для оценки.

Важно разделять качество Retrieval и качество итогового ответа.

Если поиск не находит нужный фрагмент, языковая модель может не получить информацию, необходимую для правильного ответа. Поэтому оценка должна учитывать не только качество генерации, но и качество поиска по базе знаний.

### Текущие ограничения

1. Основной режим поиска — BM25. Он зависит от текстового соответствия запроса и документов.
2. Семантический поиск через embeddings предусмотрен отдельным компонентом, но полноценный гибридный режим требует реализации и проверки.
3. Качество ответа зависит от полноты и структуры исходной базы знаний.
4. Полный сквозной запуск Qwen через Ollama необходимо проверить в целевом окружении.
5. Интеграция с Web-приложением и внешними системами не входит в подтверждённый функционал текущего AI-ядра.

Автоматические тесты проверяют отдельные компоненты и интеграционные сценарии. Успешное прохождение тестов не заменяет проверку полного сценария с работающей языковой моделью.
