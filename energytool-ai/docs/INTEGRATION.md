# Передача коллегам: пункты 4–8

## Публичный Python API

Рабочая директория/import path: energytool_hackathon/app. Пример синхронный;
для асинхронного веб-сервера используйте worker/thread, не блокируйте event loop.

```python
from integration.interface import EnergytoolAI

ai = EnergytoolAI()
try:
    first = ai.chat("После второй смены счёт вырос. Что проверить?")
    second = ai.chat("Четвёртая ценовая категория", session_id=first["session_id"])
    fresh = ai.chat("Новая задача")  # без прежнего ID — новая сессия
finally:
    ai.close()
```

chat(message: str, session_id: UUID-string | None) возвращает dict:

| Поле | Как использовать |
| --- | --- |
| answer | Единственный основной клиентский текст |
| status | Действие backend, перечень ниже |
| question | Может быть None даже при вопросе в answer; не добавлять второй вопрос автоматически |
| session_id | Сохранять в состоянии текущего чата |
| sources | Список id/path/file использованных фрагментов; для debug, не доказательство правильности |
| debug | timings_ms, elapsed_ms, reason_code, факты, цитаты, проверки, ошибки; набор зависит от ветки |

Статусы: answered, clarification_needed, handoff, no_evidence, out_of_scope,
error. Smalltalk отображается как answered. При error не сообщайте клиенту,
что вопрос не входит в компетенцию: это технический сбой. Некорректный UUID
и неверный тип message могут вызывать ValueError; HTTP-обёртка должна
преобразовать ошибки ввода в понятный ответ. Готового HTTP-сервиса здесь нет.

## Пункт 4 — заявка

Уже есть запрос человека, pending_handoff, отмена и локальное сохранение
телефона/почты в lead со status=saved_locally. Handoff не означает, что
сформирована полная заявка или контакт куда-то отправлен. Нужно добавить
ФИО, компанию, проверку заполненности, резюме и отображение готовой заявки.
Используйте отдельный структурированный объект с session_id и историей;
не меняйте смысл существующих статусов. ФИО/компания сейчас не обязательны
для локального контакта, поэтому считать эту ветку готовым пунктом 4 нельзя.
Реальная CRM по ограничениям кейса не обязательна; используйте тестовые данные.

## Пункт 5 — контекст и история

JSON-сессии сохраняют и диалоги без заявки. «Новый диалог» должен прекратить
передачу старого session_id, а не удалять прежний файл. После закрытия чата
также создавайте новую сессию. UUID — идентификатор, не механизм авторизации:
связывание с пользователем и доступ к истории обеспечивает будущий backend.
Для проверки всех сессий нужен интерфейс просмотра. Простая файловая память
не защищает от одновременной записи нескольких запросов в одну сессию;
сериализуйте такие запросы или добавьте подходящее хранилище и блокировки.

## Пункт 6 — скорость

Переиспользуйте экземпляр ядра, не стройте индекс на каждое сообщение.
Измеряйте поиск/LLM/повторы отдельно и ограничивайте параллелизм под ресурсы.
Source-ветки быстрее свободной генерации, но локальную 4B нельзя сравнивать
по скорости с платформенной 27B. Не обещайте общую задержку 0,2 секунды.

## Пункт 7 — веб-чат и debug

Нужно реализовать отправку, ожидание ответа, ошибки, новый диалог и историю.
В обычном чате показывайте answer. Debug-панель берёт время и sources из
результата API; полное содержимое debug не нужно показывать каждому клиенту.
Не выдавайте ответ повторно из question. Не храните секреты в frontend.

## Пункт 8 — встраивание

Предлагаемая граница: виджет сайта → HTTP backend → EnergytoolAI →
локальное хранилище заявки/истории. Веб-команда определяет маршруты,
авторизацию, CORS, хранение и упаковку развёртывания. Это план интеграции,
а не уже реализованные HTTP endpoint, Docker или CRM.

Перед слиянием проверьте настоящие многотуровые сценарии, сброс, заявку,
отмену, изоляцию пользователей и поведение при недоступности модели.
