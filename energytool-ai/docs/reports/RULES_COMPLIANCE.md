# Проверка допустимости инструментов и изменений

Проверены все 17 страниц `МТС_кейс.pdf`, оба приложенных DOCX,
выданный `requirements.txt` и учебный `sample_submission/solution.py`.
Слайды 9 «Пространство решений» и 10 «Ограничения» также просмотрены визуально.
Название «Пространство решений» в этих материалах относится к слайду 9;
ссылки на отдельный сайт у этого раздела нет.

Ссылка на онлайн-регламент из PDF проверена через веб-инструмент, но документ
не открылся. Поэтому актуальность его онлайн-редакции не подтверждена;
выводы ниже относятся к локально предоставленным материалам.
Исходные документы не изменялись и не загружались в публичные хранилища.

## Разрешённые методы

| Инструмент / изменение | Локальная разработка | Автоматическая проверка |
| --- | --- | --- |
| Python, стандартная библиотека, собственный BM25 | Допустимо | Допустимо; дополнительные модули должны быть корневыми `.py` |
| NumPy 2.2.6, httpx 0.28.1, python-dotenv 1.1.1 | Допустимо | Все три версии есть в выданном списке зависимостей |
| Dense BGE-M3, hybrid BM25+dense, RRF | Допустимо | Прямо разрешены любые методы RAG; BGE-M3 доступна через прокси |
| Локальная Ollama и Qwen3 4B Instruct | Допустимо по слайду 9, п.1 | Генерация должна использовать Qwen3.8-27B через API организаторов |
| Локальный LLM-reranking чатовой Qwen | Допустим как эксперимент | Не заменяет проверку специализированного Qwen3 Reranker 8B |
| Специализированный Qwen3 Reranker 8B через API | Необязателен | Доступен через тот же прокси, использование необязательно |
| Выбор фактов, точные цитаты, проверка чисел и условий | Допустимо | Регламент §7 поручает команде контроль достоверности |
| Несколько компонентов с одной моделью | Допустимо | Слайд 9, п.4; ответы вебинара №29 и №42 |
| Структурированные сведения клиента и управление вопросами | Допустимо | Сценарий проектирует команда; сведения клиента только из диалога |
| Дополнительные веб-источники о продуктах | Не используются для ответов | Приоритет у предоставленной базы, слайд 10 и вебинар №22, №39 |

Для новых изменений не нужны другие модели, сторонние сервисы, внешние
продуктовые сведения или библиотеки сверх разрешённого набора. Выбор цитат
и свободный пересказ выполняются той же моделью генерации. Для структурированных
задач в доработке от 16 ноября 2026 добавлено формирование ответа приложением
из найденных цитат: проверка порогов, минимальных данных, перечни подготовки
и диагностический шаг. Другая модель и внешние продуктовые сведения для этого
не используются; LLM для остальных ответов сохраняется. В локальном
профиле это `qwen3:4b-instruct-2507-q4_K_M`; в платформенном — значение из LLM_MODEL/GEN_MODEL/OPENAI_MODEL.
Специфические функции Ollama не являются обязательными для работы алгоритма.
В локальном адаптере JSON Schema ограничивает поля ответа обоих этапов.
Прокси организаторов получает обычный `response_format=json_object`,
а контракт проверяется приложением. Необязательный режим `local` с
sentence-transformers для платформы не используется; в зависимости ZIP
эта библиотека не включается.

## Требования к достоверности

- Слайд 10, п.2–3: свойства, цены, тарифы и условия только из базы;
  сведения клиента только из диалога; отсутствие ответа нельзя заполнять
  собственными знаниями модели.
- Вебинар №4 и №30: тематически похожий документ не должен становиться
  основанием для неподтверждённой рекомендации.
- Вебинар №13: универсальная анкета квалификации не требуется;
  вопросы зависят от продукта, задачи и ситуации.
- Вебинар №25: источники допустимы в отладке, внутренние имена и ID
  не нужны в обычном ответе.
- Вебинар №29 и №42: отдельный компонент проверки достаточности допустим,
  архитектуру следует выбирать экспериментально.

Проверка наличия цитаты и её чисел — проверка происхождения сведений.
Она не доказывает смысловую корректность каждого пересказа: это отдельно
проверяется на реальных ответах, неоднозначных и провокационных вопросах.

## Различие прототипа и автоматического сабмита

Обычное приложение хранит пакеты `rag/`, `consultant/`, сессии и локальные
настройки. В таком виде его нельзя считать готовым ZIP-сабмитом.
Технический регламент §3–6 требует отдельную точку входа, которая читает
DATA_DIR/questions.csv и knowledge-base.zip и создаёт submission.csv с
колонками id,answer, без переноса состояния между ID.
В окружение переносятся только корневые `.py` и requirements.txt.

Слайд 9 и вебинар №32 разрешают готовые индексы, а §4 технического регламента
запрещает включать файлы данных/индексов. Для совместимости выбран вариант,
который не требует разрешения этого противоречия: индекс строится из
переданной платформой базы во время запуска. Локальные кеши, веса моделей,
.env, вопросы, образцы ответов и база в автоматический ZIP не включаются.

Ограничения автоматического запуска: 20 минут, 8 CPU, 16 GB RAM, ZIP до 128 MB.
Дополнительные вызовы модели разрешены, но их задержка входит в общий бюджет.
Реальное время и качество Qwen3.8-27B нельзя подтвердить локальным прогоном 4B.
Вебинар №38 говорит, что отдельный тестовый доступ к прокси не предоставляется.

Полный финальный прототип также требует HTML-чата, сбора заявки,
истории сессий и комплекта Docker. Проверка допустимости RAG-методов
не означает, что эти самостоятельные части уже реализованы.

## Что добавлено для соблюдения контракта

`tools/build_submission.py` строит `dist/platform.zip`: импорты внутренних
пакетов преобразуются в импорты корневых `et_*.py`.
`solution.py` внутри ZIP — отдельная точка входа CSV, а локальный
`solution.py` приложения сохраняет прежний Python API.
Сборка не содержит документов базы, примеров ответов, локальных индексов,
конфигураций, секретов, моделей или дополнительных зависимостей.

Отдельный тест исполняет именно плоскую сборку вне каталога исходного
приложения, через управляемый OpenAI-совместимый API. Он проверяет
имя модели из окружения, отсутствие параметров Ollama, ID с ведущими нулями,
историю внутри кейса, изоляцию между кейсами и fallback на BM25 после
ошибки embeddings. Реальный endpoint организаторов не проверен.
